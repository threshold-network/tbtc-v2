= Threshold cross-chain - Polygon

This package is deprecated and kept only for Polygon exit operations. Do not
use it to configure new Polygon bridge-in routes. Existing Polygon tBTC
liquidity should be withdrawn through `PolygonWormholeGateway.sendTbtc` and
routed back to Ethereum before moving through the supported hub path.

The deprecation path keeps the withdrawal/burn path available while blocking
new canonical Polygon mints and routing. After this change the only exit route
from Polygon is chain 2 (Ethereum); all direct Polygon-to-L2/Solana routes are
blocked to prevent further tBTC leakage.

- set `PolygonWormholeGateway.updateMintingLimit(0)` so inbound Wormhole
  transfers no longer mint canonical Polygon tBTC;
- block Polygon peer mappings on Base, Arbitrum, Optimism, and Polygon gateway
  contracts by setting them to each gateway contract's `DISABLED_GATEWAY`
  sentinel;
- remove Polygon from new Solana gateway initialization and disable the existing
  Solana gateway Polygon peer with `cross-chain/solana/deploy/deprecate_polygon.ts`
  after the upgraded Solana Wormhole Gateway program is deployed;
- keep `PolygonTBTC` unpaused. The gateway minter role is NOT revoked by the
  automated deprecation flow; governance must manually revoke it once the
  outstanding Polygon exit surface is fully drained.

Any tBTC still inbound to Polygon after deprecation will be effectively locked
or require manual recovery; do not establish new inbound bridges to Polygon.

For fresh deployments, the deploy scripts apply these settings before gateway
ownership is transferred. For existing live deployments where gateway ownership
has already been transferred, governance must execute the equivalent
`updateMintingLimit(0)` and `updateGatewayAddress(..., DISABLED_GATEWAY())`
calls on the EVM gateway contracts after those contracts are upgraded. The
EVM mapping scripts skip the gateway block if the deployed gateway is not
upgraded with `DISABLED_GATEWAY()` support yet; set
`REQUIRE_DISABLED_GATEWAY_SUPPORT=true` to make that precondition fatal for a
deprecation-specific run. The Solana cleanup script refuses to disable the
Polygon peer unless the deployed Anchor IDL contains the `GatewayDisabled`
error and the `gatewayInfo` account on the `sendTbtcWrapped` instruction.

For historical context, this package originally brought Bitcoin to Polygon via
the Wormhole Token Bridge. See
link:https://github.com/keep-network/tbtc-v2/blob/main/docs/rfc/rfc-8.adoc[RFC 8: Cross-chain Tokenized Threshold BTC].

== How it worked (pre-deprecation)

```
+----------------------------+         +---------------------------------------------------------------------------+
|          Ethereum          |         |                                Polygon                                   |
|                            |         |                                                                           |
|  +----------------------+  |         |  +----------------------+  +-------------------------+  +--------------+  |
|  | Wormhole TokenBridge |--|---------|--| Wormhole TokenBridge |--| PolygonWormholeGateway |--| PolygonTBTC |  |
|  +----------------------+  |         |  +----------------------+  +-------------------------+  +--------------+  |
|                            |         |                                                                           |
+----------------------------+         +---------------------------------------------------------------------------+
```

- `PolygonTBTC` canonical tBTC token on Polygon with a minting authority
delegated to `PolygonWormholeGateway`.
- `PolygonWormholeGateway` is a smart contract wrapping and unwrapping 
Wormhole-specific tBTC representation into the canonical `PolygonTBTC` token.

=== Updating Wormhole Gateway mapping

With deprecation, the gateway mapping is updated using a sentinel-block flow.
The deployment scripts (e.g., 13-16_block_..._in_wormhole_gateway_mapping.ts,
plus the sibling packages' own 14_block_polygon_in_wormhole_gateway_mapping.ts)
are responsible for blocking peers by setting the mapping to the
`DISABLED_GATEWAY` sentinel value, ensuring no further transfers can be
initiated to those chains. Additionally, `sendTbtcGateway` calls to a zero
address are rejected, ensuring that no peer is configured for that gateway.

=== Deploy contracts

To deploy all contracts on the given network, please run:
```
yarn deploy --network <network>
```

Supported networks:
- `hardhat` - for local development
- `mumbai` - testing network
- `polygon` - mainnet

Currently, this module does not deploy any contracts on L1. All the existing 
Wormhole contract addresses that are used in this module are stored under 
`external/<network>` dir.

If contracts haven't been built yet or changes occurred, `deploy` task will build
the contracts before running the deployment script. This command produces
an `export.json` file containing contract deployment info. Note that for the
chains other than `hardhat` the following environment variables are needed:

- `SIDECHAIN_API_URL` - URL to access blockchain services, e.g. `https://polygon.g.alchemy.com/v2/<alchemy_api_key>`
- `SIDECHAIN_ACCOUNTS_PRIVATE_KEYS` - Private keys for the deployer and council `<0xOwnerPrivKey,0xCouncilPrivKey>`
- `POLYGONSCAN_API_KEY` - Polygonscan API key
