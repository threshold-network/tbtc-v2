= Threshold cross-chain - Optimism

This package is deprecated and kept only for Optimism exit operations. Do not
use it to configure new Optimism bridge-in routes. Existing Optimism tBTC
liquidity should be withdrawn through `OptimismWormholeGateway.sendTbtc` and
routed back to Ethereum before moving through the supported hub path.

The deprecation follows the Polygon one. It keeps the withdrawal/burn path to
Ethereum (chain 2) and blocks new canonical Optimism mints and direct routes:

- set `OptimismWormholeGateway.updateMintingLimit(0)` so inbound Wormhole
  transfers no longer mint canonical Optimism tBTC. This call works on the
  gateway as deployed today and does not need an upgrade;
- block the Arbitrum, Base and Solana peers on the Optimism gateway, and the
  Optimism peer on the Arbitrum and Base gateways, by setting them to each
  gateway contract's `DISABLED_GATEWAY` sentinel (Polygon already blocks every
  peer);
- register Optimism with the `DISABLED_GATEWAY` sentinel on new Solana gateway
  initialization (an unregistered peer would still accept raw Wormhole tBTC
  sends), and disable the existing Solana gateway Optimism peer with
  `cross-chain/solana/deploy/deprecate_optimism.ts` after the upgraded Solana
  Wormhole Gateway program is deployed;
- keep `OptimismTBTC` unpaused. The gateway minter role is not revoked by the
  automated flow; governance revokes it once the outstanding Optimism supply has
  drained.

With the minting limit at zero, a Wormhole transfer that still reaches the
Optimism gateway is not minted: the gateway hands the receiver the Wormhole tBTC
representation instead, which can be bridged back to Ethereum through the
Wormhole Token Bridge.

For live deployments, gateway ownership already sits with governance, so
governance executes the equivalent calls. `34_manual_deprecate_optimism_wormhole_gateway.ts`
prints their calldata, and `governance/update-minting-limit-zero.safe-batch.json`
is a Safe Transaction Builder batch with `updateMintingLimit(0)` for the
Optimism gateway owner Safe. `updateMintingLimit(0)` can be executed right away; the
`updateGatewayAddress(..., DISABLED_GATEWAY())` calls need the upgraded gateway
implementation. The cross-chain packages deploy and upgrade gateways from the
pinned `@keep-network/tbtc-v2` release (1.4.0-dev.0 or 1.7.2), which predates
`DISABLED_GATEWAY`: release a package with this `L2WormholeGateway`, bump the
pins, upgrade the gateways, then run the mapping scripts. Until then the EVM
mapping scripts probe the deployed gateway and skip the block, on Hardhat dry
runs too; run them with `--tags DeprecateOptimism` or
`REQUIRE_DISABLED_GATEWAY_SUPPORT=true` to make that precondition fatal.

For historical context, this package originally brought Bitcoin to Ethereum L2
Optimism. See
link:https://github.com/keep-network/tbtc-v2/blob/main/docs/rfc/rfc-8.adoc[RFC 8: Cross-chain Tokenized Threshold BTC].

== How it worked (pre-deprecation)

```
+----------------------------+         +---------------------------------------------------------------------------+
|          Ethereum          |         |                                Optimism                                   |
|                            |         |                                                                           |
|  +----------------------+  |         |  +----------------------+  +-------------------------+  +--------------+  |
|  | Wormhole TokenBridge |--|---------|--| Wormhole TokenBridge |--| OptimismWormholeGateway |--| OptimismTBTC |  |
|  +----------------------+  |         |  +----------------------+  +-------------------------+  +--------------+  |
|                            |         |                                                                           |
+----------------------------+         +---------------------------------------------------------------------------+
```

- `OptimismTBTC` canonical tBTC token on Optimism with a minting authority
delegated to `OptimismWormholeGateway`.
- `OptimismWormholeGateway` is a smart contract wrapping and unwrapping 
Wormhole-specific tBTC representation into the canonical `OptimismTBTC` token.

=== Updating Wormhole Gateway mapping

For supported routes and the Sepolia/Solana deployment policy, see
link:../wormhole-routing.adoc[Wormhole routing policy].

The deployment scripts are responsible for managing updates of the tBTC gateway
addresses across various chains. These addresses are stored in the `external/`
directory for a specific network, such as `optimismSepolia/ArbitrumWormholeGateway.json.` 
It is important to note that these addresses should remain constant for the 
mainnet network. However, there may be instances where a new version of a 
cross-chain module is deployed to the testing network, which would require a 
manual update of the corresponding address.

=== Deploy contracts

To deploy all contracts on the given network, please run:
```
yarn deploy --network <network>
```

Supported networks:
- `hardhat` - for local development
- `optimismSepolia` - L2 testing network
- `optimism` - L2 mainnet

Currently, this module does not deploy any contracts on L1. All the existing 
Wormhole contract addresses that are used in this module are stored under 
`external/<network>` dir.

Historical Goerli-era deployment records are retained in `external/` for
reference; those networks are no longer configured for deployment.

If contracts haven't been built yet or changes occurred, `deploy` task will build
the contracts before running the deployment script. This command produces
an `export.json` file containing contract deployment info. Note that for the
chains other than `hardhat` the following environment variables are needed:

- `L2_CHAIN_API_URL` - URL to access blockchain services, e.g. `https://optimism-sepolia.infura.io/v3/<infura_api_key>`
- `L2_ACCOUNTS_PRIVATE_KEYS` - Private keys for the deployer and council `<0xOwnerPrivKey,0xCouncilPrivKey>`
- `OPTIMISM_ETHERSCAN_API_KEY` - Optimism Etherscan API key
