# Slither triage for the reservation surface.
#
# One row per Slither finding inside the bar's own scope,
# solidity/contracts/bridge/, with the verdict and the reason.
# The bar tbtc-v2.slither.findings counts the in-scope findings
# that carry no row here, so a row is how a finding leaves the
# count. check-slither-triage.js reads this file.
#
# Format, pipe separated:
#   id | detector | file | symbol | verdict | reason
#
# `symbol` is the function, event or state variable the detector
# names first, never a line, because lines move with every
# reformat and a symbol does not.
#
# `verdict` is one of:
#   false-positive  the detector's claim does not hold here
#   accepted        the claim holds, and the finding is accepted
#                   with the written reason and no change in this
#                   release
#   open            a real issue that must be fixed or decided; it
#                   stays in the bar count

SL-049 | encode-packed-collision | contracts/bridge/Deposit.sol | _revealDeposit | accepted | True positive of the static pattern, not a reachable collision. The packed string is the exact Bitcoin transaction serialization, so an equal hash implies an equal byte string and the only freedom is where the input and output vectors are split. Every consumer pins the parsed vectors first: Deposit._revealDeposit and WalletProposalValidator.validateDepositExtraInfo compare the extracted output script hash against a 160-bit hash of a script whose 20-byte parts come from the on-chain deposit key, and BitcoinTx.validateProof canonicalises with validateVin and validateVout before the merkle check, so a shifted split cannot reach a different amount or a different key. The expression must also stay byte-identical between the bridge and the validator, because the validator recomputes the key the bridge recorded.
