== Build, test and deploy

tBTC v2 contracts use https://hardhat.org/[*Hardhat*] development environment.
To build and deploy these contracts, please follow the instructions presented
below.

=== Prerequisites

Please make sure you have the following prerequisites installed on your machine:

- https://nodejs.org[Node.js] >14.17.4
- https://yarnpkg.com[Yarn] >1.22.10

=== Build contracts

To build the smart contracts, install node packages first:
```
yarn install
```
Once packages are installed, you can build the smart contracts using:
```
yarn build
```
Compiled contracts will land in the `build` directory.

*NOTE:* The `tbtc-v2` package contains an indirect dependency to
`@summa-tx/relay-sol@2.0.2` package, which downloads one of its sub-dependencies
via unathenticated `git://` protocol. That protocol is no longer supported by
GitHub. This means that in certain situations installation of the package or
update of its dependencies using Yarn may result in `The unauthenticated git
protocol on port 9418 is no longer supported` error. +
As a workaround, we advise changing Git configuration to use `https://` protocol
instead of `git://` by executing:
```
git config --global url."https://".insteadOf git://
```

=== Test contracts

There are multiple test scenarios living in the `test` directory.

You can run unit tests with:
```
yarn test
```

The tests marked as "pending" during `yarn test` are integration tests.

You can run integration tests with:

```
yarn test:integration
```

System tests are implemented separately, in the
link:../system-tests/[`system-tests`] directory of the `tbtc-v2` repository.

=== Measure test coverage

Run coverage from this package directory:

[source,sh]
----
env -u FORKING_URL -u FORKING_BLOCK yarn coverage
----

Reports appear in `coverage/lcov.info`, `coverage/coverage-final.json`,
and `coverage/lcov-report/index.html`. Test harness contracts are excluded.

The coverage script uses the Prague hardfork because instrumented deployments
can exceed Osaka's per-transaction gas cap. Coverage also permits oversized
contracts. Normal tests keep the default hardfork and contract size limit.
Instrumentation changes gas use, so gas and reimbursement assertions can fail
under coverage. Use normal tests, not coverage, for those assertions.

The script also clears `FORKING_URL` and `FORKING_BLOCK` for its own run. A
forking network changes the deployment path: the external exports then refuse to
deploy their stub contracts (they throw `deployed NuCypherToken contract not
found`), so deployment fixtures fail. A coverage run that inherits a fork URL
from the shell is a forking run, not a coverage problem; the script makes that
impossible.

=== Deploy contracts

To deploy all contracts on the given network, please run:
```
yarn deploy --network <network>
```

If contracts haven't been built yet or changes occurred, this task will build
the contracts before running the deployment script. This command produces
an `export.json` file containing contract deployment info.

==== Wormhole L2 BTC redeemer initializer

L2BTCRedeemerWormhole.initialize stores a non-zero, deployment-supplied Wormhole chain ID for the L1 BTC redeemer. requestRedemption rejects a caller-supplied recipientChain unless it matches that stored value, preventing callers from redirecting a redemption. The contract does not verify the configured ID is canonical, so deployment and upgrade procedures must supply the correct Wormhole chain ID.

```
initialize(
  address _tbtc,
  address _gateway,
  bytes32 _l1BtcRedeemerWormholeAddress,
  uint16 _l1BtcRedeemerWormholeChain
)
```

Deployment scripts must pass the canonical Wormhole chain ID (see
https://docs.wormhole.com/wormhole/reference/chain-ids[Wormhole docs Chain IDs]
for a reference). The initializer reverts if the provided chain ID is 0.

*Deployment and Upgrade:*
- *Fresh deployment:* Provide a non-zero chain ID to `initialize(...)`.
- *Existing proxy upgrade:* To upgrade, bundle the implementation upgrade with an
  owner-only `initializeV2(uint16)` call into a single governance batch. This
  ensures the `l1BtcRedeemerWormholeChain` is set atomically, preventing redemptions
  from failing closed in the interim.

Post-deployment, the owner can atomically repoint the destination via
`updateL1BtcRedeemer(bytes32, uint16)`.
