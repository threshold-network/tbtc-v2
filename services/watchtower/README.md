# P2TR Signature-Fraud Watchtower

Production service scaffold for the tBTC P2TR signature-fraud challenge path.

The package wraps the SDK watchtower runner with process-level boundaries that an operator service needs:

- durable JSON persistence for challenge records with changed-since-load overwrite guards;
- state-file validation before restart replay or challenge submission;
- one integrated cycle that replays stored challenges, scans Bitcoin transaction sources, applies Bridge lifecycle events, and returns a single summary;
- cycle metrics for source failures, per-item failures, observations, submission attempts, lifecycle records, and unresolved operator alerts;
- an abort-aware sequential polling loop that prevents overlapping cycles and makes cycle failures explicit;
- an observation-only default for process-level service cycles unless challenge submission is explicitly enabled;
- a bundled Esplora-backed transaction source for registered P2TR wallet addresses;
- a bundled Ethers-compatible Bridge lifecycle event source for P2TR challenge defeat and timeout events;
- dependency injection points for Bitcoin transaction discovery, Bridge lifecycle event discovery, and challenge submission.

This package is intentionally scoped to the Schnorr FROST/ROAST P2TR fraud path. It does not depend on account-control, ac-watchdog, or covenant packages.

## Operator Wiring

A production deployment must provide these adapters:

- `BitcoinClient`: resolves input prevouts for candidate Bitcoin transactions.
- `P2TRSignatureFraudWatchtowerTransactionSource`: lists mempool and confirmed candidate P2TR spends.
- `P2TRSignatureFraudWatchtowerBridgeLifecycleEventSource`: lists Bridge challenge lifecycle events.
- `P2TRSignatureFraudChallengeSubmitter`: submits the on-chain P2TR signature-fraud challenge transaction. Required only when challenge submission is explicitly enabled.
- `P2TRWatchtowerChallengeRecordPersistence`: stores serialized challenge records durably.

`EsploraP2TRSignatureFraudTransactionSource` can be used as the Bitcoin transaction source for observation-mode rehearsals and single-process deployments. It derives Bech32m P2TR wallet addresses from canonical x-only wallet IDs, reads Esplora mempool and confirmed address transaction pages, and also requires a Bridge adapter exposing `getTaprootDepositRevealedEvents` and `deposits`. The adapter scans every revealed Taproot deposit for the registered wallets, reads the stored extra data needed to reconstruct its unique output key, and queries the exact Esplora funding outpoint for its spend. Transactions found through wallet addresses and deposit outpoints are deduplicated before raw transaction hex is fetched for the SDK runner. A failed reveal-history read, deposit request, outspend lookup, or per-candidate raw-transaction fetch is isolated from the remaining deposits and base-wallet scan; construction therefore also requires an `onDepositScanFailure` callback so every skipped item is routed to structured operator logging or alerting. Raw-transaction failures include the spending transaction ID and, when the candidate came from a deposit outpoint, its funding transaction ID and output index; wallet-only failures omit the funding fields. Failure callbacks must be non-blocking; an exception from the callback is contained by the source. The reveal source must return the complete canonical event history on every scan; the bundled adapter does not cursor deposit events because an old unspent deposit must remain monitored indefinitely. It does not resolve prevouts by itself; deployments must still provide a `BitcoinClient` for that. It also does not replace Bridge lifecycle event discovery or challenge submission.

`EthersP2TRSignatureFraudBridgeLifecycleEventSource` can be used with an Ethers-compatible Bridge contract instance. It reads `P2TRSignatureFraudChallengeDefeated` and `P2TRSignatureFraudChallengeDefeatTimedOut` logs over a configured block range, or derives `toBlock` from the contract provider and a configured confirmation depth. It rejects unsafe range options, can enforce a maximum numeric block span per scan, normalizes the on-chain `challengeKey` to the watchtower's stored Bridge challenge key, and emits key-addressed lifecycle events. When the Bridge logs include wallet ID, Bridge challenge identity, or sighash arguments, the source carries those fields into the lifecycle event so the SDK runner can reject transitions whose Bridge-emitted evidence does not match the persisted observation. Timeout logs default to both `slashed` and `rewarded` records because the Bridge timeout transaction resolves the challenge, slashes the wallet, and rewards the notifier; embedding services can opt into a single timeout status if an approved Bridge integration needs narrower tracking. After a challenge is recorded as timeout-eligible or slashed, repeated observations cannot resubmit it; stale timeout or defeat events cannot move slashed records backward, and only the corresponding reward record can advance a slashed record. Embedding services can provide a scan cursor store and a cursor overlap window for conservative reorg replay; cursor-backed scans require `maxBlockRange` plus either a numeric `toBlock` or provider-derived confirmation depth, reject explicit `fromBlock` overrides, and require overlap to be smaller than `maxBlockRange` so durable cursor deployments cannot silently rescan an uncommittable, unbounded, or non-progressing range. If `requireCursorBlockHash` is enabled, the source validates the previous cursor block hash before querying, pins the current scan boundary block hash before querying, and refuses to commit the cursor if that scan-boundary hash changes after the logs are processed. If a cursor-backed scan has more confirmed blocks available than `maxBlockRange`, the source scans and commits one bounded window so catch-up can proceed over multiple cycles. The watchtower service commits the cursor only after Bridge lifecycle events are listed and processed without source or per-event failures. The adapter does not compute timeout eligibility or replace final production event-indexing and reorg policy.

`FileBackedP2TRBridgeLifecycleScanCursorStore` persists the Bridge lifecycle scan cursor as `{ lastScannedBlock, lastScannedBlockHash? }`, validates the cursor before use, rejects overwrites when the cursor file changed since the last load, and replaces the file atomically on save. It is suitable for single-process dry runs and operator rehearsals. Multi-process or horizontally scaled deployments should replace it with a transactional cursor store and an approved reorg policy.

`FileBackedP2TRWatchtowerChallengeRecordPersistence` is suitable for single-process dry runs and operator rehearsals. It validates serialized records when loading the state file, before restart replay or challenge submission, and rejects overwrites when the state file changed since the last load. Multi-process or horizontally scaled deployments should replace it with a transactional store while preserving the same SDK persistence contract.

`loadP2TRSignatureFraudWatchtowerRuntimeConfig` provides a small environment-shaped configuration boundary for operator deployments. It validates the durable state path, registered wallet IDs, Bridge domain identifier, optional Bridge challenge domain, Esplora transaction-source settings, Bridge lifecycle scan window/cursor settings, poll interval, retry limits, and failure policy before the service starts.

`createFileBackedP2TRSignatureFraudWatchtowerRuntime` wires that validated runtime config into `P2TRSignatureFraudWatchtowerService`, a file-backed persistence instance, and loop options for single-process deployments.

`createEsploraP2TRTransactionSourceFromRuntimeConfig` wires validated Esplora base URL, Bitcoin network, timeout, retry, and confirmed-page settings into the bundled Esplora transaction source using the registered wallet IDs from runtime config. Its runtime options require the same complete-history Taproot deposit reveal source and structured deposit-scan failure handler used by direct construction.

`createFileBackedP2TRBridgeLifecycleEventSource` wires the validated Bridge lifecycle runtime config into the Ethers-compatible event source and uses `FileBackedP2TRBridgeLifecycleScanCursorStore` when `P2TR_SIGNATURE_FRAUD_WATCHTOWER_BRIDGE_LIFECYCLE_CURSOR_FILE` is configured.

## Cycle Contract

Each `processCycle()` call:

1. reloads persisted challenge records through the serialized SDK store;
2. replays stored observed, submitting, and rejected challenges that are still eligible for submission;
3. scans mempool and confirmed Bitcoin sources;
4. applies Bridge defeated, timeout-eligible, slashed, and rewarded events;
5. emits metrics plus the SDK's final challenge summary and unresolved operator alerts.

The service treats source failures separately from per-transaction and per-event failures so an operator can distinguish upstream outages from malformed candidate data. Source-failure logs include source names and errors; item-failure logs include transaction hashes, confirmed block metadata, or Bridge lifecycle event details without dumping raw Bitcoin transaction payloads. Bridge lifecycle resolution clears stale open or acknowledged submission-attempt alerts once a challenge is defeated, slashed, or rewarded.

## Polling Loop

`runP2TRSignatureFraudWatchtowerLoop` runs one cycle at a time, waits for the configured poll interval, and exits on `AbortSignal` or a configured cycle limit. Unexpected cycle errors fail the loop by default; operators can opt into `continueOnError` only when surrounding supervision and alerting are in place.

The loop is intentionally small and dependency-free so deployments can wire it into systemd, Kubernetes, a worker queue, or a custom supervisor without changing watchtower state semantics.

The SDK runner, service, and runtime config default to observation-only operation and do not require a challenge submitter in that mode. Set `P2TR_SIGNATURE_FRAUD_WATCHTOWER_SUBMIT_CHALLENGES=true` only after a production Bridge submitter is deployed, reviewed, funded, and explicitly approved. Submission startup also fails unless the embedding service supplies an approved spend-type classifier and submission policy, explicit payload bounds, a Bridge challenge domain, and a submission-attempt ceiling with an operator alert; SDK submission policies and service startup both reject `unclassified`, `wallet-closing`, and `heartbeat` spend types as fail-closed for submissions. The environment loader approves only the spend types an operator explicitly allowlists through `P2TR_SIGNATURE_FRAUD_WATCHTOWER_SUBMISSION_ALLOWED_SPEND_TYPES`, and it neither installs a classifier nor freezes production bounds by itself.

The bundled environment-backed runtime uses file-backed challenge-record and Bridge lifecycle cursor stores. Those stores are single-process rehearsal stores, not production indexing stores. If `P2TR_SIGNATURE_FRAUD_WATCHTOWER_SUBMIT_CHALLENGES=true`, the loader also requires `P2TR_SIGNATURE_FRAUD_WATCHTOWER_ALLOW_FILE_BACKED_SUBMISSION=true` so operators cannot accidentally treat the bundled file-backed runtime as production submission infrastructure. The service constructor enforces the same boundary for direct embedders: submission mode requires either `indexingStoreProfile: 'transactional-production'` or `allowSingleProcessRehearsalSubmission: true`, and the transactional-production profile requires both challenge-record persistence and the Bridge lifecycle event source to self-identify as `transactional-production` with the same non-empty transactional store ID. Bundled file-backed stores self-identify as `single-process-rehearsal` so they cannot satisfy that profile. Production submission must provide transactional challenge-record and cursor stores through an embedding service.

Embedding services can provide a `spendTypeClassifier` in service config to classify observations before submission policy checks. The SDK exposes a deterministic rule-composition helper for approved classifiers: malformed rules fail closed, no matching rule leaves observations `unclassified`, and ambiguous or non-boolean rule matches fail closed. The environment-backed runtime may parse an explicit allowed-spend-types allowlist from `P2TR_SIGNATURE_FRAUD_WATCHTOWER_SUBMISSION_ALLOWED_SPEND_TYPES` into a submission policy, but it still does not install a classifier, so env-only deployments keep observations `unclassified` and fail closed. Submission requires a code-injected `spendTypeClassifier` passed to `createFileBackedP2TRSignatureFraudWatchtowerRuntime(config, dependencies, { spendTypeClassifier })`; without it the builder throws before the service starts.

Embedding services can also provide `payloadBounds` to reject oversized raw transactions, input/output counts, and scriptPubKey byte lengths before observations are recorded. Challenge submission requires `maxRawTransactionBytes`, `maxInputs`, `maxOutputs`, and `maxScriptPubKeyBytes`. The environment-backed runtime does not freeze those values; production deployment still needs reviewed bounds before submission is enabled.

When an embedding service provides `bridgeChallengeDomain`, or when the environment-backed runtime receives both Bridge challenge-domain variables, the watchtower derives a structured Bridge challenge identity from the verifier payload and stores the domain-separated Bridge challenge key alongside the observation so submitters and Bridge lifecycle sources can use the same key material. Bridge lifecycle events can then identify a challenge by either the off-chain observation ID or the stored Bridge challenge key; key-only events are resolved through the durable challenge records and fail closed if the key is unknown or ambiguous. When lifecycle events include wallet ID, Bridge challenge identity, or sighash evidence, the SDK runner compares those fields with the stored observation before applying the lifecycle state change. The environment-backed runtime does not infer this domain automatically.

Before challenge submission, stored observations are reconstructed from their witness data using the configured Bridge identifier, classifier, payload bounds, and Bridge challenge domain. A restarted service with mismatched config or a mutated persisted observation fails closed before calling the submitter.
